# CU-01 — Comercios, usuarios, perfiles y permisos

**Dictamen:** **CU-01 cerrado según el modelo acordado.** La matriz no deja pendientes funcionales de implementación y el recorrido de navegador para comercio y operador terminó. Esto no afirma que el equipo/docente haya aceptado la diferencia con la letra del taller ni certifica la titularidad de todos los datos persistentes heredados.

## Letra del taller y decisión vigente

La fuente es **docs/alcance/Calcs/Casos de Uso - Responsables.xlsm**, hoja **CU obligatorios**, fila 4: CU-01, “Comercios y usuarios”; requisito: “ABM de comercios y usuarios, perfiles y permisos.”; módulo/pantalla: **Backoffice**; responsable: **Operador / administrador**; obligatoriedad: **Obligatorio**.

Esa ubicación literal pone la administración de comercios en el Backoffice del operador. El modelo actual del equipo toma otra decisión de producto: cada comercio se autogestiona desde Commerce; cada operador administra solamente su propia organización desde Backoffice; Admin representa a la plataforma para soporte y altas administrativas. La diferencia queda explícita para que el equipo/docente determine su aceptación académica. No se concede al operador acceso para administrar comercios.

### Decisión vigente del modelo

- El comercio elige **cualquier operador disponible para cada envío**. El envío conserva ComercioId y OperadorId elegidos; no hay relación permanente comercio–operador, membresía previa ni tabla de clientes del operador.
- El operador consulta los envíos asignados a su OperadorId. No administra la organización, usuarios, roles ni permisos del comercio.
- El comercio administra sus propios usuarios, roles y permisos en Commerce; el operador, los suyos en Backoffice. Admin realiza operaciones de plataforma.
- La baja es una **suspensión no destructiva**: conserva organización, accesos, roles, envíos e historial. No existe borrado físico en estos recorridos.
- La edición de organización expone el nombre y la versión de concurrencia porque Nombre es el único campo descriptivo actual del modelo; no se presenta como un perfil comercial más amplio.
- Roles y permisos siguen siendo de NexoRuta y están limitados a la organización. No se convierten en roles globales de Identity.

Esta es la decisión de alcance vigente para CU-01; no reescribe los ADR históricos archivados en PDF. El aislamiento técnico por tenant sigue [ADR-MT-001 — PostgreSQL RLS](../../../docs/alcance/ADR-MT-001-PostgreSQL-RLS.md), que también define al envío como vínculo por ComercioId y OperadorId elegido para cada envío.

## Implementación actual

**Cuentas y autenticación.** ASP.NET Core Identity con el almacén EF Core estándar administra las cuentas y contraseñas persistidas. La entidad Identity Usuario conserva los GUID existentes en la tabla Usuarios; no hay dos cuentas que deban sincronizarse ni una segunda tabla AspNetUsers paralela. Identity administra creación, validación y edición de correo. La API conserva su contrato de JWT; Commerce, Backoffice y Admin mantienen sus cookies protegidas y envían el Bearer desde el servidor. La API no autentica usuarios con un header de selección/demostración: las rutas privadas requieren JWT y vuelven a comprobar identidad, acceso, estado y permisos persistidos.

**Autogestión y autoridad de plataforma.** El registro crea primero una identidad sin organización. Esa identidad autenticada puede crear su comercio u operador; el alta crea organización, acceso dueño y rol inicial dentro del flujo transaccional y exige un nuevo login para recibir el contexto organizacional. Admin puede crear y consultar comercios y operadores, administrar su estado y resolver solicitudes como autoridad de soporte; el alta propia no depende de Admin.

**Usuarios y dueño.** La API permite listar y crear empleados, activar/desactivar accesos, cambiar correo de empleados y gestionar roles/grants según permisos dinámicos de la organización. La gestión no permite modificar correo, estado, rol ni rol protegido del dueño, ni siquiera por el propio dueño. Esta regla se verifica tanto en API como en las pantallas. EsPropietario es hoy una propiedad persistida y usada por las comprobaciones de propiedad; no es sólo una marca histórica ni se deriva del nombre del rol.

**Aislamiento.** La API deriva el contexto del JWT validado y del acceso persistido. RlsTransactionMiddleware lo establece como contexto transaccional antes de acceder a tablas protegidas. PostgreSQL aplica RLS a las tablas de negocio con ENABLE y FORCE; comercio y operador comparten únicamente los envíos cuyo ComercioId u OperadorId corresponda, incluyendo sus hijos. El operador elegido se determina por envío. Las tablas globales de Identity no son datos tenant. Ver [guía sencilla de RLS](../../../docs/rls/README.md) y [auditoría RLS](../../../docs/rls/AUDITORIA.md).

**Límite de seguridad.** El rol de ejecución puede modificar las variables GUC nexoruta.* mediante SQL arbitrario. RLS no prueba la autenticidad de esos valores y no protege frente a una inyección SQL que permita falsificar el contexto; la guía de auditoría documenta esta limitación.

## Límites de datos y aceptación académica

- **Datos heredados sin dueño verificado:** la migración de propiedad no inventa un dueño cuando el historial no lo demuestra. En ese caso la organización se puede consultar, pero la edición y solicitudes reservadas al dueño quedan deshabilitadas. La prueba frontend OwnerlessOrganizationPagesRemainReadOnlyAndExplainWhy fija esa conducta. En esta auditoría no se consultó ni escribió la base persistente, por lo que no se afirma cuántas organizaciones reales están en esa situación. Si existen, requieren una decisión de titularidad explícita; no se deben elevar administradores automáticamente. Es un límite de datos no censados, no un pendiente de código demostrado por la matriz.
- **No es una deuda obligatoria de CU-01 según la letra revisada:** recuperación de contraseña, invitaciones, borrado físico, múltiples accesos por identidad y SSO no se contabilizan como pendientes de este caso. OIDC no se presenta como implementado: el modelo escogido usa Identity para las cuentas y mantiene el JWT existente.
- **No se obtuvo aceptación académica** de la diferencia entre Backoffice del operador indicado en la planilla y autogestión del comercio en Commerce. Esa decisión corresponde al equipo/docente; no se oculta ni se atribuye al código una aprobación que no ocurrió.

## Verificación de esta auditoría (2026-10-18)

- Backend Release: `dotnet build NexoRuta.sln --configuration Release --verbosity minimal` pasó con 0 advertencias y 0 errores. Suite completa: 3 pruebas de arquitectura + 103 unitarias + 290 de integración = **396/396**, sin fallos ni omisiones. La suite de integración usa PostgreSQL efímero. Ejecución RLS enfocada: **33/33**, sin fallos ni omisiones, con el rol restringido.
- Frontend Release: build con 0 advertencias y 0 errores; suite completa: **219/219**, sin fallos ni omisiones, incluidas las pruebas de páginas y contratos OpenAPI.
- `dotnet ef migrations has-pending-model-changes`: no hay cambios de modelo pendientes.
- Se validaron **32 enlaces relativos de documentación/diagramas en 12 archivos**; todos los destinos existen, incluidos los diagramas originales enlazados desde `docs/rls/README.md`. `git diff --check` pasó en raíz, backend y frontend.
- Navegador real disponible (Microsoft Edge). `node scripts/check-onboarding-browser.mjs` terminó con **código 0**: verificó autogestión de Commerce y Backoffice, roles/usuarios, dueño de solo lectura, formularios de Admin aprobar/rechazar, alta propia de ambos tipos y suspensión/reactivación de Commerce con nuevo login. `node scripts/check-reactivation-browser.mjs` terminó con **código 0** para **comercio y operador**: solicitud del dueño, rechazo de Admin, resultado visible al dueño, reintento, aprobación de Admin, login nuevo y página operativa mostrando la organización activa. Ambos scripts arrancaron PostgreSQL efímero, aplicaron migraciones allí con `SeedData=false` y luego crearon la cuenta de plataforma con el comando soportado `platform-admin create`; no dependieron de seeders generales ni de credenciales locales.
- El primer intento de reactivación había fallado en el login operativo final y mostraba `ReturnUrl=/not-found`, sin exponer un estado HTTP concluyente. La revisión del fixture encontró que el recorrido podía exceder el límite real de cinco logins por minuto y reutilizaba la cookie de la sesión restringida. Los fixtures esperan una ventana del limitador y limpian la cookie antes del login nuevo. El recorrido completo posterior pasó para ambos tenants; no quedó reproducido un defecto de producto.
- La revisión independiente detectó que el bootstrap de terminal asumía Windows. Se corrigió el fixture para usar la API de consola de Windows solo en Windows y `stty -echo` con restauración en POSIX; esta ruta POSIX quedó revisada por código, pero no se ejecutó en un host POSIX. Después de esa corrección, `node scripts/check-onboarding-browser.mjs` y `node scripts/check-reactivation-browser.mjs` terminaron con **código 0** en Edge; la reactivación cubrió comercio y operador y onboarding cubrió autogestión/alta propia de ambos tipos. La suite backend enfocada `SolicitudesReactivacionHttpTests|SuspensionSessionHttpTests` pasó **7/7**, sin omitidas, en PostgreSQL efímero. `node --check` y `git diff --check` también pasaron. Las suites completas y verificaciones de modelo/documentación listadas arriba corresponden a la auditoría del mismo checkout; no se volvieron a ejecutar en esta continuación.
- No se ejecutaron migraciones ni seeders contra PostgreSQL persistente, no se escribieron datos persistentes y no se recrearon servicios de Compose. Tanto las pruebas de integración como ambos recorridos de Edge usaron bases efímeras propias.

La matriz no tiene pendientes funcionales bajo el modelo actual y ahora cuenta con evidencia HTTP y de navegador para los recorridos descritos. Por eso el dictamen es **CU-01 cerrado según el modelo acordado**, no “aceptado por el docente”. Quedan explícitamente fuera de lo que esta auditoría puede certificar la aceptación académica de la ubicación literal en Backoffice y el número/estado de organizaciones persistentes sin dueño verificable; no se consultó la base persistente. Si existen, la UI/API mantiene esos registros en solo lectura hasta que se resuelva la titularidad de forma explícita.
